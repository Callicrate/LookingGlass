## Executive assessment

Rookery is unusually well tested and carefully bounded for a local, single-user project. Its queue, ingestion, migration, packaging, command, and browser controls have substantial direct evidence behind them. The project is not generally sloppy.

The main release claim nevertheless does not survive a fresh browser-level security test. The process-unique `*.localhost` activation origin is not actually reserved by the Rookery process across loopback address families. On the reviewed Windows and Chrome path, Rookery can own `127.0.0.1:<port>` while another local process owns `::1:<port>`. Chrome selected the IPv6 listener for the random `.localhost` hostname. JavaScript served by that listener read the synthetic activation fragment, and the resulting token was accepted by Rookery's real bootstrap path.

That is a complete local authorization bypass, not a cosmetic cookie concern. It directly contradicts the architecture's “process-local session” claim and makes release clearance conditional.

The review found:

|---|---:|---|
| Critical | 0 | None confirmed |
| High | 1 | Opposite-family loopback listener can steal and redeem browser activation |
| Medium | 2 | Foreign SQLite files are changed/copied before identity validation; durable files lack current-user access hardening |
| Low | 1 | Standalone wheel smoke and locked audit validate different dependency graphs |

## Detailed findings

### CR-01: Opposite-family loopback listener can steal and redeem activation

**Severity:** High
**Confidence:** High
**Evidence quality:** A, direct browser/socket reproduction
**Category:** Security architecture, authentication boundary

#### Observed evidence

Rookery publishes one random browser origin but binds only the configured address:

- `src/async_api_view/config.py:25` defaults `host` to `127.0.0.1`;
- `src/async_api_view/cli.py:154` prints `http://<random>.localhost:<port>/bootstrap#<token>`;
- `src/async_api_view/cli.py:207` passes only `settings.app.host` to Uvicorn;
- `src/async_api_view/web/auth.py:64` creates the random `rookery-<32 hex>.localhost` name;
- `src/async_api_view/web/app.py:414` exposes bootstrap redemption before session authentication;
- `src/async_api_view/web/app.py:424` issues the session cookie after redemption.

A disposable socket probe successfully bound both `127.0.0.1:<random-port>` and `::1:<same-port>` in one process. Headless Chrome then navigated to the random `.localhost` URL and selected only the IPv6 listener:

```text
{'port': 14506, 'hits': ['ipv6'], 'exit': 0, 'dom_ipv4': False, 'dom_ipv6': True}
```

The IPv6 listener returned JavaScript that copied `location.hash` into the DOM. Chrome executed it and exposed the synthetic fragment:

```text
{'hits': ['ipv6'], 'exit': 0, 'synthetic_fragment_read': True}
```

The captured synthetic token was then submitted through Rookery's actual app with its real Host and Origin checks:

```text
{'status': 303, 'session_cookie_issued': True, 'dashboard_after_redeem': 200}
```

The existing cookie-isolation test does not cover this. It uses an in-process test transport and explicitly confirms that a cookie is sent to the same random hostname on another port. It never creates competing IPv4/IPv6 listeners or runs a real browser resolver.

#### Attack path

1. Rookery binds `127.0.0.1:8765` and prints a random `.localhost` URL.
2. Another local process binds `::1:8765`, which is a different socket namespace entry.
3. The operator opens the legitimate printed URL.
4. Chrome resolves the special-use `.localhost` host to loopback and selects the attacker-owned IPv6 listener.
5. The attacker serves JavaScript that reads the fragment. URL fragments are hidden from HTTP, but not from the page receiving the navigation.
6. The attacker replays the token to `127.0.0.1:8765` using the random Host and matching Origin.
7. Rookery issues a valid session. The attacker can read cached state and submit every refresh action available to the operator.

#### Impact

This bypasses the entire browser authorization boundary. It exposes cached remote metadata and local operational history and grants refresh authority. Single-use and ten-minute expiry determine who wins the race; they do not contain the resulting session.

#### Counter-evidence and scope

- The attack requires a local process and operator activation during the bootstrap window.
- It is not a remote-network exploit.
- Address-family selection was reproduced on Windows with Chrome. Other browser/OS combinations may choose differently.
- `HttpOnly`, `SameSite=Strict`, CSRF, TrustedHost, random hostname, session expiry, and output escaping otherwise held up.
- The architecture assumes operating-system account permissions protect the bootstrap channel. The reproduced socket collision crosses a boundary those permissions do not reserve.

#### Smallest credible repair

Reserve and serve both `127.0.0.1` and `::1` on the chosen port before printing the activation URL. If either bind fails, exit without disclosing a token. Keep the random hostname for cookie isolation.

Changing the configured host from `127.0.0.1` to `localhost`, tightening Host/Origin checks, or adding `Secure` to the cookie does not reserve the sibling address family and does not fix this path.

#### Verification needed

- Start Rookery with a real browser while an opposite-family listener attempts the same port.
- Prove either Rookery owns both families and receives the request, or startup fails before token disclosure.
- Run the regression on Windows/Chrome and Ubuntu/Chromium.
- Verify session cookies and fragments never reach a competing listener during activation or subsequent navigation.

### CR-02: Foreign SQLite files are changed and backed up before identity validation

**Severity:** Medium
**Confidence:** High
**Evidence quality:** A, direct disposable-database reproduction
**Category:** Data safety, file trust boundary

#### Observed evidence

`SQLiteStore` opens the configured file write-capable and enables WAL before migration-time identity validation:

- `src/async_api_view/storage/sqlite.py:558` opens the database;
- `_enable_wal_mode()` runs before `_migrate()` and `_validate_database_identity()`;
- `backup_sqlite_database()` at `src/async_api_view/storage/sqlite.py:351` verifies file shape and SQLite integrity, but not the Rookery application identity.

A disposable foreign database started in `DELETE` journal mode. Rookery rejected it, but only after changing it to WAL and creating sidecars. The backup command then published a copy containing the foreign row:

```text
{
  'before_mode': 'delete',
  'rejected_as': 'DatabaseError',
  'after_mode': 'wal',
  'sidecars': ['.sqlite3-shm', '.sqlite3-wal'],
  'foreign_value_preserved': True,
  'backup_published': True,
  'copied_foreign_value': True
}
```

#### Impact

An operator typo in `app.database_path` can persistently alter another application's SQLite journal behavior and create sidecars even though Rookery reports rejection. `backup` can copy an unrelated database, potentially duplicating sensitive data under a misleading Rookery recovery operation.

This requires local configuration/operator error rather than remote input, which limits severity to medium.

#### Smallest credible repair

- For every existing database, perform a read-only Rookery identity/schema preflight before opening write-capable or changing journal mode.
- Apply the same identity preflight to backup sources.
- Bind the preflight and subsequent use to the same resolved file identity where the platform permits, reducing replacement races.

#### Verification needed

- A foreign database in `DELETE` mode remains byte/logically unchanged, remains in `DELETE`, and gains no WAL/SHM sidecars after rejected `init`, `run-once`, or `serve`.
- `backup` rejects the foreign file and publishes no destination.
- Empty new databases, valid markerless legacy Rookery databases, and valid current WAL databases still initialize, migrate, and back up.

### CR-03: Database files are not protected to the single-user boundary

**Severity:** Medium
**Confidence:** High
**Evidence quality:** A, direct ACL/mode observation
**Category:** Local data confidentiality and integrity

#### Observed evidence

`SQLiteStore.__init__()` creates the parent and database but never hardens directory or file access. This is unlike the Databricks CLI work-root code, which explicitly applies current-user ownership and ACL/mode restrictions.

Direct checks found:

- under a normal POSIX `0022` umask, a Rookery-created state directory had mode `0755` and its database had mode `0644`;
- the actual reviewed Windows database inherited an ACL granting a local sandbox group modify access;
- the backup directory inherited the same group-level modify access.

The database can contain remote object names, paths, identifiers, provenance, action history, errors, and operational metadata. Group/world read is a confidentiality issue. Group modify permits direct tampering with cached state outside the browser/session authorization path.

#### Impact

The product is described as local and single-user, but its durable state does not enforce that boundary. Another local principal may read cached remote metadata or modify the local source of truth if parent defaults are permissive.

#### Smallest credible repair

- On POSIX, require a mode-`0700` state directory and mode-`0600` database, WAL, SHM, and backup files.
- On Windows, establish and verify current-user ownership plus a protected current-user DACL for the state directory and published backups.
- Fail closed on redirected/reparse paths or files whose ownership cannot be established.
- Document any explicit opt-in shared-storage mode separately rather than inheriting it accidentally.

#### Verification needed

- Regression tests pre-create permissive parents/files and prove permissions are corrected or startup fails.
- Verify database, WAL, SHM, temporary backup, and published backup permissions on Windows and Linux.
- Prove hardening does not follow symlinks/junctions or replace unrelated files.

### CR-04: Standalone wheel smoke and dependency audit cover different graphs

**Severity:** Low
**Confidence:** High
**Evidence quality:** A for the validation gap; no current vulnerable resolved package was found
**Category:** Supply-chain verification

#### Observed evidence

- CI runs `uv audit --locked`, which audits `uv.lock`.
- The isolated wheel verifier creates a new environment and runs `uv pip install <wheel>` without the lockfile or a runtime constraints file.
- Wheel metadata allows ranges such as `fastapi>=0.115,<1`, `jinja2>=3.1,<4`, and `uvicorn>=0.30,<1`.
- The verifier checks importability, assets, CLI help, `init-config`, and `init`, but does not audit the packages actually resolved into that environment.
- Dependabot is configured only for GitHub Actions, not Python/uv dependencies.

#### Impact

The source-checkout graph can be locked and clean while the standalone wheel smoke installs a different compatible graph. A future vulnerable or behaviorally incompatible release can enter the standalone path without being represented by the lock audit.

No current dependency vulnerability was found, so this is a validation blind spot rather than an active compromise.

#### Smallest credible repair

- Add one installed-wheel smoke using an exported, hash-pinned runtime constraints set derived from `uv.lock`.
- Audit the actual isolated wheel environment after installation.
- Keep a separate range-resolution compatibility job if testing newest allowed dependencies is desired.
- Add automated Python/uv dependency update proposals with the full gate.

#### Verification needed

- Compare installed distributions and versions to the expected locked runtime set.
- Make a deliberately vulnerable or mismatched compatible test package fail the isolated audit.
- Keep the unconstrained compatibility job clearly labeled so it is not confused with reproducible release verification.

## What holds up

The review confirmed these strengths:

- **Queue and lifecycle correctness:** lease expiry/recovery, retry promotion, coalescing, final authorization, lifecycle outage reporting, and exact-expiry handling have direct tests and coherent transaction boundaries.
- **Ingestion integrity:** capability/scope authority, batch identity, collisions, partial rollback, source ordering, completeness watermarks, multipart chunking, and residue-free rejection are strongly defended.
- **Schema safety after identity is established:** migration, repair, application ID, index/trigger validation, and rollback behavior are unusually thorough.
- **Web controls apart from CR-01:** TrustedHost, same-origin enforcement, per-session CSRF, server-side opaque sessions, idle/absolute expiry, autoescaping, bounded forms, safe return paths, and security headers are directly tested.
- **Command boundary:** the Databricks worker uses structured argv, a closed command map, absolute executable resolution, controlled environment/cwd, output/time limits, cancellation reaping, and diagnostic redaction.
- **Secrets and crypto:** no committed credential or private key was found. No project certificate is present. SHA-256 is used for integrity/opaque-token digesting, not password storage; token comparison is constant-time.
- **Package contents:** the source/wheel asset inventory, checkout-free initialization, CLI surface, and current archive hashes verified.
- **Documentation honesty:** live Databricks auth/inventory, restore, Workspace content persistence, automatic scheduling, Linux SSH, and compaction are labeled unverified or deferred.
- **Current validation:** fresh Windows run passed 453 tests with one documented skip, 89% branch coverage, clean Ruff/security/performance lint, clean lock/audit, compatible installed dependencies, and verified 82/61/30 archives/assets.

## Material omissions and residual risk

These are not promoted as additional defects because the project labels most of them honestly:

- No live Databricks authentication, authorization, inventory, pagination, or rate-limit behavior has been exercised.
- Restore remains unsupported. Backup integrity is not equivalent to recovery readiness.
- Evidence/action history remains uncompacted; long-lived database growth lacks a completed retention owner.
- Phase 4 automatic scheduling and core metrics are not implemented.
- Workspace content encryption, access policy, retention deletion, and artifact storage remain fail-closed/deferred.
- The current review reran the full Windows gate but did not independently rerun the final Ubuntu/WSL gate.
- Browser exploit evidence is direct for Windows/Chrome. Other browser/OS address-family choices remain to be characterized.

- **“454 collected contradicts 453 tests.”** Rejected. The fresh result is 453 passed plus one skipped test, exactly 454 collected.
- **Broad loopback authorization failure without a concrete path.** Replaced by the narrower, reproduced dual-stack finding CR-01. Host, Origin, CSRF, and session checks themselves held up.

## Decision impact and repair order

1. **Block browser-session release clearance on CR-01.** The authentication boundary is bypassable on the reviewed platform.
2. **Fix CR-02 before describing foreign-database rejection as non-mutating or safe.** Operator error must not alter another application's file.
3. **Fix CR-03 before relying on “single-user local” as a durable confidentiality/integrity control.**
4. **Close CR-04 as release engineering hardening.** It should not delay a controlled local developer build after the security/data findings are fixed.

After CR-01 through CR-03, rerun:

- real browser dual-stack activation tests on Windows and Ubuntu;
- foreign/legacy/current database identity tests;
- Windows/POSIX permission tests for database sidecars and backups;
- the exact Windows/Ubuntu full gate and installed-wheel verifier.

## CodeGuard security assessment

CodeGuard was applied because this project contains authentication, session cookies, web forms, SQLite storage, command execution, secrets handling, CI, packaging, and serialization boundaries.

- **Hardcoded credentials:** none found. Test fixtures use synthetic placeholders and assert non-persistence.
- **Cryptography:** no banned or deprecated encryption/signature algorithm is used. SHA-256 token digests are appropriate for high-entropy opaque capabilities; `secrets` provides CSPRNG tokens; `hmac.compare_digest` is used.
- **Certificates:** no project certificate or private key was found, so certificate expiry/key/signature checks were not applicable.
- **Authentication/session:** most controls are strong, but CR-01 defeats the bootstrap transport/origin ownership assumption.
- **Authorization/input/injection:** deny-by-default session middleware, CSRF/Origin/Host checks, bounded allow-listed forms, parameterized SQL, and structured process execution held up.
- **Storage/privacy:** CR-02 and CR-03 are the material gaps. Backups and databases need identity and access hardening.
- **Logging:** durable diagnostics are bounded, redacted, and control-character sanitized. Process logs remain mostly free-form, but no secret leak was reproduced.
- **Supply chain:** actions and build requirements are pinned; CR-04 identifies the remaining installed-graph mismatch.
- **Serialization:** shared JSON depth/container/node/cycle bounds and residue-free digest rejection held up.
