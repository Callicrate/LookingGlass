## Scope and decision

This pass reviews whether the durable migration ledger proves the exact migration bytes that produced the local schema and data, not only the ordered version names. It covers source checkout and installed-wheel migration resources, DDL and DML-only edits, missing/extra files, rollback, backup/reopen, and legacy checksum adoption.

Applied migration bytes are release authority. A current binary must fail before new mutation when its known historical migration content disagrees with the store's durable provenance. Legacy stores may adopt current reviewed hashes only when their schema/ledger already match the recognized current migration chain; adoption must be atomic with normal startup validation.

## Findings

### F1 — High: applied migration versions did not prove the bytes that produced the store

The prior `schema_migrations(version, applied_at)` ledger accepted any current resource with a known version. Existing DDL comparison could catch many schema edits, but a historical DML-only edit could silently change replay behavior while reopening a database produced by different bytes.

Repair: package 27 canonical SQL resources behind a hard-pinned `MANIFEST.sha256`; derive a domain-separated ordered hash chain; persist version, ordinal, content digest, byte count, chain digest, basis, and timestamp in migration `0027`; validate any present provenance before new mutation; and finalize execution/adoption inside the outer startup transaction. A regression changes historical DML bytes while updating its temporary manifest/build pin and proves reopen fails before database mutation.

### F2 — Medium: dynamic migration discovery had no canonical inventory contract

The earlier sorted glob did not independently bind the exact resource set or require a unique contiguous ordinal sequence. Packaging loss, an extra SQL file, or ambiguous numbering could therefore reach migration logic without one immutable inventory authority.

Repair: exact manifest bytes are pinned in code; manifest syntax, LF termination, ASCII encoding, SQL UTF-8, exact filenames, contiguous ordinals, unique payload digests, and head version are all checked before write-capable open. Missing, extra, reordered, duplicate-ordinal, and malformed resources have direct regressions.

### F3 — Low: a platform-specific coverage artifact could enter the sdist

The first isolated WSL gate used `.coverage-wsl-final`, which was neither ignored nor forbidden. Hatch and the verifier consistently treated that untracked file as intended source, producing a truthful but wrong 98-entry archive.

Repair: ignore the complete `.coverage*` family and independently reject coverage reports, coverage data, HTML coverage, pytest/Ruff caches, and bytecode cache paths in distribution verification. The generated file was removed, a regression proves rejection, and repeated packages returned to 97 sdist entries.

### F4 — Medium: legacy adoption could bless an incomplete derived read projection

Independent review reproduced a valid durable relationship with its `relationship_read_index` row removed. Schema, SQLite integrity, and foreign keys all passed; the candidate then adopted migration 0025 while `readable_relationships` exposed nothing.

Repair: before any legacy ledger adoption, reconcile the complete relationship read index against durable relationships and current object types inside the startup transaction. The regression removes the projection row, reopens the legacy store, and requires the child relationship to be readable again before provenance finalization.

### F5 — Medium: basis and recording time could be mistaken for authenticated evidence

The content chain is externally anchored by installed package bytes, but `basis` and `recorded_at` are necessarily local observations. The first candidate allowed either label and any canonical timestamp on reopen, so a direct database writer could relabel an execution row without changing the byte chain.

Repair: rename the compatibility label from `state_adopted` to the narrower `ledger_adopted`; reject normal provenance updates and deletes with schema triggers; and document that basis/timestamp are descriptive local metadata, not an authenticated audit against an owner who can rewrite the SQLite file. Exact version/content/chain fields remain verified against the installed build on every open.

### F6 — Low: installed-wheel smoke checked digest shape instead of exact values

The first checkout-free smoke checked contiguous ordinals, `executed`, and 64-character digest lengths. Runtime validation made bogus values unlikely, but a regression in that same runtime path could let length-correct junk satisfy the package gate.

Repair: the verifier now independently reads the wheel's manifest and SQL members, recomputes every content digest, byte count, and domain-separated chain value without importing runtime migration code, and compares the complete deterministic database rows.

## Decision and compatibility boundary

- Fresh databases record all 27 rows as `executed`.
- A recognized legacy store through 0026 cannot retroactively prove which historical DML bytes ran. It is accepted only after current schema validation, startup recovery, rebuildable relationship-read reconciliation, SQLite integrity, and foreign-key checks, and those 26 rows are labeled `ledger_adopted`; migration 0027 is labeled `executed`. This is an honest compatibility bridge, not a historical-execution claim.
- A store that already has a provenance table must match the exact current prefix before startup can mutate it; incomplete or drifted provenance is not repaired automatically.
- Migration execution, version insertion, recovery needed before adoption, provenance insertion, schema validation, and application-ID assertion remain in one immediate transaction. Injected migration failure leaves DDL, the version ledger, and provenance unchanged.
