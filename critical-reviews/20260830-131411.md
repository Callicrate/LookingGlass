## Scope and decision

This pass reviews the authenticated local browser workflow as an operational product: activation, cached dashboard, refresh form, intent polling, authorization expiry, low-headroom unavailability, error recovery, no-JavaScript fallback, narrow viewport, keyboard access, and truthful state transitions. It preserves the loopback/session trust boundary and current dense dashboard visual language.

The decision is patch-after-review. Every browser navigation should stay in an accessible Rookery shell, protected writes must fail closed without becoming raw API output, cached state must remain visible when refresh is unavailable, controls must expose why they are disabled, polling must stop or recover truthfully, and the main workflow must remain usable without JavaScript.

## Workflow and state audit

- Primary operator: one local user repeatedly reading cached state and occasionally requesting refresh.
- Entrypoint: one process-scoped `.localhost` activation URL; one opaque server-side session.
- Main action: inspect trust banner and authority, choose one enabled refresh, land on durable intent receipt, observe terminal state, return to dashboard/action detail.
- JavaScript enhancement: disables submitted button and polls intent status; server routes remain the source of truth.
- Required unavailable states: worker startup/failure, storage headroom, expired browser session, malformed request, unknown object/action/intent, and local state failure.

## Findings

### Finding 1: low, expired no-JavaScript form submission leaves the product shell

Status: closed.

An expired protected GET rendered the accessible unlock/restart page, but an expired refresh POST returned raw JSON. With JavaScript disabled, or during ordinary full-page form navigation, the operator left the Rookery shell and received no product-specific recovery path. The backend remained protected, so this is a workflow/accessibility defect rather than an authorization defect.

Repair: unauthenticated non-API routes now render the bootstrap recovery shell for every method; `/api/` remains JSON for polling clients. Direct expired POST and the complete unauthenticated-surface matrix require HTML recovery, cookie clearing, no backend submission, and JSON only for API polling.

### Finding 2: medium, polling labels server state errors as transport disconnection

Status: closed.

The polling script threw the same generic error for every non-403 non-2xx response. API 503 and 500 therefore appeared as “Disconnected,” even though transport was healthy and local intent state was unavailable; API 404 retried forever instead of navigating to the accessible HTML not-found shell.

Repair: 403 and 404 reload into the relevant HTML recovery/error route. Server 5xx uses a distinct “Status unavailable” warning state with bounded backoff while cached receipt data stays visible. Only fetch/parse failures use the red disconnected state. The pulse gains a non-animated warning class and reduced-motion selector coverage.

### Finding 3: medium, server-rendered terminal receipts start polling again

Status: closed.

A terminal intent page rendered “Final state” but initialized the active green pulse and unconditionally scheduled its first poll. A later 5xx could therefore demote known-final state to “Status unavailable” and retry, contradicting the page's stop contract.

Repair: the server emits explicit terminal data and the final pulse class; JavaScript sets final state and returns before registering a timer. TestClient verifies terminal markup. Rendered Chrome held final state after the prior polling interval, issued no API request, and had a clean console.
