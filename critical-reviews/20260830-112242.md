## Scope and decision

This pass asks whether Rookery preserves enough local storage headroom to stop safely before durable SQLite, WAL, event, and backup writes fail together. It also adjudicates the one transient Windows access-denied result from the standalone verifier's disposable-environment rename. Full retention/compaction and restore remain separate product capabilities unless current evidence proves they are required for the smallest safe repair.

The decision is patch-after-review. Any headroom guard must keep read-only cached state available, disable or reject new work truthfully, recheck before remote dispatch, permit terminalization and recovery writes, remain deterministic in tests, and avoid claiming that filesystem free-space APIs prove quota-level capacity.

## Findings

### Finding 1: medium, no pre-exhaustion fence protects remote result persistence

Status: closed after ordering re-review.

New intent insertion, coordinator action admission, and final dispatch had no available-capacity check. A deterministic `SQLITE_FULL` probe accepted fourteen ordinary intents and failed the fifteenth. More importantly, an admitted action could still consume remote read/quota work before discovering that its normalized batch, attempt, terminal state, and durable outage event could not be written.

Counterevidence limits severity: refreshes are manual, collection/output sizes are bounded, and uncompacted growth is documented. The missing boundary is still operationally material because failure occurs after remote work.

Repair: use quota-aware caller-available bytes through an injectable platform probe. Preserve a floor of `max(64 MiB, 2 × CLI output cap)` after one output-sized planned write. Disable UI options without hiding cached state; preserve idempotent duplicate intent reads; defer queued scopes; recheck action admission; and move final-dispatch actions to retry-wait without executing the CLI. Cleanup, cancellation, attempts, completion, outage events, and shutdown remain unfenced so they can consume the reserve.

Initial re-review found the first implementation checked headroom before invalid-scope rejection and before final cancellation/satisfaction. The check now occurs only before creating a new action and immediately before transitioning an otherwise valid unsatisfied action to `running`. Regressions require low-headroom invalid scopes to reject and disabled bindings to cancel instead of deferring.

### Finding 2: medium, online backup can consume the active-state reserve

Status: closed.

The online backup temporary file is created on the destination volume without a capacity preflight. If that destination shares the nearly full state volume, the temporary snapshot can consume the space needed by concurrent WAL and terminal writes even though failed-backup cleanup is otherwise careful.

Repair: derive snapshot bytes from SQLite `page_count × page_size`, never sparse-file logical length, and require that amount plus a 64 MiB destination reserve before creating the temporary copy. Probe failure blocks backup conservatively and publishes nothing.

### Adjudication: verifier rename access denial

No finding. Five clean-clone repetitions passed, synchronous subprocess ownership is bounded, and the original traceback did not preserve a handle owner. If the failure recurs, retain the exact failing rename and capture the bounded handle owner before attributing it to repository code or the environment.
