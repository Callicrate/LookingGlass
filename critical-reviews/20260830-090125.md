## Finding 1: medium, standalone prerequisites omit online dependency resolution

Confidence: high  
Evidence quality: A

Status: closed. Standalone documentation now requires the matching constraints plus index, complete cache, or reviewed wheelhouse and explicitly denies a self-contained offline bundle claim.

The README says the standalone path needs the wheel, Python 3.12, `uv`, and the Databricks CLI. The wheel contains dependency ranges for FastAPI, Jinja2, and Uvicorn, but no dependency wheels, runtime constraints, or lock. With an empty disposable uv cache, the documented tool install and force-upgrade fail under `--offline` because FastAPI cannot be found.

Online installation works and currently resolves allowed versions that differ from `uv.lock`, such as Click 8.5.0 versus locked 8.4.2 and Pydantic 2.13.5 versus 2.13.4. Range resolution is not itself a demonstrated behavior defect, and offline failure preserves an existing installed command, but the listed standalone prerequisites are incomplete.

Repair shape: state explicitly that standalone installation and upgrade require an accessible Python package index or a pre-populated uv cache. Do not imply that the wheel is a self-contained offline bundle. If offline installation becomes a supported goal, publish a pinned/hash-verified wheelhouse plus an exact offline command and regression.

Verification: documentation and installed-package smoke agree; online Python-pinned install/force-upgrade pass; empty-cache offline failure is described rather than claimed supported; uninstall still preserves operator configuration.

## Finding 2: medium, post-start CLI incompatibility leaves refresh controls enabled

Confidence: high  
Evidence quality: A

Status: closed. Worker-global incompatibility/runtime failures safely terminalize the action then reach supervision; controls disable, one outage event is recorded, doctor retries, and recovery re-enables controls. Profile-local unavailability remains action-scoped.

Executable witnessing correctly rejects a changed or uncertified CLI before mapped dispatch. `DatabricksWorker.process`, however, catches `CliIncompatible` or certification-related `CliUnavailable` as an ordinary action failure. The exception never reaches the runtime supervisor that owns worker availability.

A composed runtime started healthy, accepted a refresh, and then received `CliIncompatible` from runner execution. The action safely terminalized as failed, but `runtime.worker_available` stayed true, the dashboard did not show refresh unavailable, and controls remained enabled. This contradicts the documented compatibility-retry behavior.

Repair shape: after safely recording the affected attempt/action failure, re-raise worker-global execution failures to the supervisor. The supervisor must mark worker unavailable, disable controls, emit one outage transition, retry doctor with bounded backoff, and recover only after certification succeeds.

Verification: a composed post-start executable-witness failure records one failed action, disables controls with a worker explanation, emits one redacted worker event, repeatedly fails doctor while incompatible, and re-enables controls only after successful recertification.

## Finding 3: medium, standalone installs do not execute the audited lock graph

## Finding 6: medium, tool constraints pin versions but do not enforce hashes

Confidence: high  
Evidence quality: A

Status: closed. Standalone dependencies install through `uv pip --require-hashes --no-build`; a deliberately corrupted selected dependency hash fails in a fresh environment and leaves the active environment usable.

Pinned uv accepts exact versions from `uv tool install --constraints`, but that surface does not enforce hashes in the constraints file. Corrupting the selected Click wheel hash still installed successfully with source builds disabled on Windows and WSL. `UV_REQUIRE_HASHES=1` did not change tool behavior, and `uv tool install --require-hashes` is unsupported. The equivalent `uv pip install --require-hashes --no-build -r ...` correctly rejected the artifact.

Repair shape: use a dedicated private venv. Populate its complete runtime graph with `uv pip install --require-hashes --no-build -r runtime-constraints.txt`, then install or force-reinstall the Rookery wheel with `--no-deps`. Verify the exact freeze, interpreter, CLI, and a deliberately corrupted-hash rejection.

## Finding 7: medium, untracked package bytes can receive a false commit manifest

Confidence: high  
Evidence quality: A

Status: closed. Manifest publication checks all tracked and untracked files. Ignored `dist/` remains allowed; untracked package/root source bytes and `GITHUB_SHA` mismatch fail release publication.

The commit-manifest repair checked `git status --untracked-files=no`, while source verification deliberately included untracked, unignored files. An untracked module under `src/async_api_view` entered the wheel; tracked-only status still appeared clean; manifest publication then claimed `HEAD` and hashed the contaminated wheel.

Repair shape: require a completely clean checkout including all untracked files before commit-qualified publication. Ignored `dist/` remains excluded normally. Add a regression that an untracked package or root source file prevents manifest creation and fails CI release publication.

## Finding 8: medium, in-place upgrades retain removed executable packages

Confidence: high  
Evidence quality: A

Status: closed. Upgrades build and smoke a fresh relocatable sibling with exact freeze, then swap through recoverable renames while retaining the prior environment. A synthetic prior-only package with executable `.pth` hook runs before upgrade and is absent afterward.

Applying new constraints inside the existing private environment pins listed packages but does not remove packages absent from the new graph. A prior-only package remained after the documented upgrade; a prior-only setuptools installation left a `.pth` startup hook executing on every later Python start.

Repair shape: stage each stopped upgrade in a fresh relocatable sibling environment, install hash-required dependencies and the no-deps Rookery wheel, verify exact freeze and CLI behavior, then replace the active environment through recoverable renames while retaining the prior environment for rollback. A failed staging install must leave active bytes usable.

Verification: seed the old environment with a synthetic prior-only wheel carrying an executable `.pth` hook; prove it executes before upgrade, then prove a successful fresh-environment swap removes both package and hook. Corrupted dependency hashes or wheel-install failure must leave the active environment unchanged.

## Finding 9: medium, documented PowerShell failures bypass rollback

Confidence: high  
Evidence quality: A

Status: closed. Every documented native command checks `$LASTEXITCODE`; renames use terminating errors; completed moves are tracked; post-relocation smoke is protected; and rollback failures are explicit. Injected dependency, wheel, smoke, rename, and rollback failures preserve active or clearly retain usable previous state.

PowerShell native commands do not throw on nonzero exit by default, and `Move-Item` errors are nonterminating without `-ErrorAction Stop`. In the first staged-upgrade block, corrupted dependency hashes, staging CLI failure, and post-relocation CLI failure all produced nonzero exits but execution continued; `catch` never ran and a broken sibling replaced the healthy active environment.

Repair shape: check `$LASTEXITCODE` and throw after every uv/Python/CLI invocation. Use terminating rename operations, track each successful move, include both renames and post-relocation smoke inside the protected state machine, and perform explicit failure-checked rollback based on completed moves.

Verification: execute the documented PowerShell state machine with injected dependency, wheel, staged-smoke, first/second rename, and relocated-smoke failures. Every failure must leave the original active CLI and exact freeze usable, or report an explicit rollback failure without claiming success.
