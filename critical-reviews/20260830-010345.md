## Executive assessment

Rookery's current recovery surface is careful about logical SQLite consistency, identity, permissions, no-overwrite publication, and migration rollback. The recent storage hardening survives scrutiny. Restore and compaction are also labeled as deferred rather than presented as finished.

Two operator-facing contracts still fail at their boundaries.

First, `run-once` is documented as draining eligible work and stopping, but its private loop raises after exactly 10,000 cycles even if every cycle is still making progress. This is a deliberate safety cap hidden behind an unconditional command description. At a large post-outage backlog, the command reports failure and leaves eligible work behind.

Second, `backup` proves an internally consistent SQLite copy and safely publishes a name, but it does not explicitly synchronize the validated file or containing directory before reporting success. Logical consistency is not the same as durability across a host power loss immediately after command completion.

Third, package upgrade guidance recommends replacing the installed wheel without requiring a pre-migration checkpoint or warning that the first stateful invocation automatically migrates the database and makes an older binary reject the newer ledger.

## Detailed findings

### OR-01: `run-once` does not fulfill its unconditional drain contract

- **Severity:** Medium
- **Confidence:** High
- **Evidence quality:** A, direct source and execution
**Category:** Operator contract, failure behavior

#### Observed evidence

The public help and README say `run-once` drains currently eligible coordinator and worker activity, then stops. The implementation instead loops over `range(10_000)` and raises `RuntimeError("run-once exceeded its bounded work limit")` when no idle cycle appears before the cap.

A memory-only fake runtime whose coordinator always reported one productive item and whose worker returned no work produced:

```text
run-once=run-once exceeded its bounded work limit|coordinator=10000|worker=10000
```

The CLI catches that error and returns exit code 2. Work beyond the cap remains eligible for a later invocation.

#### Counter-evidence

- The cap prevents a corrupted or self-replenishing queue from hanging forever.
- `current-status.md` has previously called the behavior “bounded run-once draining,” so the bound is intentional rather than accidental.
- The current real database has no large backlog.

#### Decision impact

An operator using `run-once` to recover a large eligible backlog after downtime can receive a failed command even though the command made healthy progress, and the documented drain is incomplete.

#### Smallest credible repair

Make the bound public and operationally truthful. Add `run-once --max-cycles N` with a safe default, return a distinct incomplete result when the limit is reached, and tell the operator to rerun. Alternatively, rename/document the command as a bounded batch. Preserve a hard upper bound.

#### Verification needed

- A 10,001-cycle case processes exactly the configured limit, reports bounded incompletion without presenting a runtime fault, and leaves one cycle for a subsequent invocation.
- An actual idle queue still exits successfully.
- Invalid, zero, boolean, or excessive limits fail before opening SQLite.

### OR-02: Backup success lacks an explicit power-loss durability barrier

- **Severity:** Medium
- **Confidence:** High that the barrier is absent; medium on filesystem-specific post-crash outcome
- **Evidence quality:** B, direct source plus authoritative operating-system contracts
**Category:** Recovery durability

#### Observed evidence

`backup_sqlite_database()` snapshots into a private temporary SQLite file, validates identity and integrity, creates a hard link at the destination, removes the temporary name, hardens and reverifies the destination, then returns it. The path is race-safe and no-overwrite, but the success path contains no explicit file or directory synchronization call.

Python documents `os.fsync()` as the operation that forces a file descriptor to disk. The Linux `fsync(2)` contract also states that synchronizing a file does not necessarily persist its containing directory entry; the directory needs its own synchronization. Windows exposes write-through move and explicit file flush APIs for the corresponding durability boundary.

Relevant primary references:

- [Python 3.12 `os.fsync`](https://docs.python.org/3.12/library/os.html#os.fsync)
- [Linux `fsync(2)` directory-entry requirement](https://www.man7.org/linux/man-pages/man2/fsync.2.html)
- [Windows `MoveFileEx` write-through behavior](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw)

#### Counter-evidence

- SQLite's online backup creates a logically consistent copy, and the destination passes `PRAGMA integrity_check` before publication.
- SQLite and the filesystem may already flush much of the underlying data during close; ordinary clean shutdowns are not the failing case.
- The primary database remains intact if the new backup name is lost.

#### Decision impact

The command can report a successful recovery copy without proving that the final file data and directory name have crossed the storage durability boundary. A sudden power loss immediately after success can therefore defeat the backup's purpose on affected filesystems.

#### Smallest credible repair

Synchronize the validated snapshot file before publication and establish a platform-specific durable publication primitive. On POSIX, synchronize the file and containing directory after name creation/removal. On Windows, use a guarded file flush and a write-through publication path that preserves no-overwrite semantics. Fail rather than claim success if a required durability barrier is unsupported.

#### Verification needed

- Ordering tests prove file flush precedes successful return and directory/publication flush follows final naming.
- Injected flush failures return an error, preserve the source, and remove only a matching unpublished snapshot.
- POSIX and Windows integration tests exercise their real durability APIs. A true power-cut test remains an environment-level acceptance test rather than a normal unit test.

### OR-03: Stateful upgrade guidance omits the one safe rollback checkpoint

- **Severity:** Medium
- **Confidence:** High
- **Evidence quality:** A, direct source and docs
**Category:** Upgrade recovery

#### Observed evidence

README recommends `uv tool install --force` for upgrades. The first later `init`, `run-once`, or `serve` constructs `SQLiteStore`, which automatically applies every pending migration. A prior binary rejects any ledger version it does not know. The project has no down migrations, target-version option, restore command, or supported in-place downgrade.

Failed migration itself is strongly atomic. The gap begins after a migration succeeds but the upgraded application later proves unusable.

#### Counter-evidence

- `backup` can snapshot a recognized older schema without migrating it.
- Schema migration, ledger writes, index repair, validation, and application-ID marking share an immediate transaction; injected failures roll back.
- Restore and broader rollout tooling are explicitly Phase 5 work.

#### Decision impact

An operator who upgrades the package and starts Rookery before taking a checkpoint can lose the ability to return to the prior executable even though all user data remains present.

#### Smallest credible repair

Make a verified backup before the first stateful command part of the upgrade contract, state that in-place downgrade is unsupported, and give exact ordering. A future release should add automatic pre-migration snapshots or a supported restore/rollback command.

#### Verification needed

- Old schema to new schema migration succeeds while preserving a pre-migration snapshot.
- The prior binary's rejection of the migrated ledger is explicit and documented.
- The documented pre-migration backup command does not itself migrate the source.

### OR-04: Long-lived storage growth is not visible in the operator runbook

- **Severity:** Low
- **Confidence:** High
- **Evidence quality:** A, direct docs and source
**Category:** Operational omission

#### Observed evidence

The architecture explicitly defers evidence compaction, checkpoint replay, alert retention, and broader operator tooling. `SQLiteStore.ingest()` states that the accepted journal is intentionally uncompacted. There is no ordinary retention delete or vacuum surface for observation/action/event history, and every manual backup duplicates the full database.

The README's recovery section explains restore limits but does not tell an operator that database history and backup count have no automatic retention policy or size alarm.

#### Counter-evidence

- The architecture clearly labels compaction as deferred and leaves exact history retention as an open question.
- Bounded current-state projections keep ordinary reads from replaying full history.
- The actual reviewed database is only 401,408 bytes with 46 rows and no freelist pages.

#### Decision impact

This is not a current incident, but a long-running operator may assume the local service and manual backup directory remain bounded without intervention.

#### Smallest credible repair

Add an operator-facing warning that history and backups are not automatically pruned, state what to monitor, and keep compaction/retention implementation in the existing Phase 5 plan. A future status surface should report database and backup bytes before automatic pruning is introduced.

#### Verification needed

- README recovery guidance names the unbounded surfaces and manual responsibility without implying unsupported retention automation.
- A later compaction implementation must prove checkpoint replay and content-retention safety before deleting evidence.

## What holds up

- Foreign databases, redirected paths, hard links, identity replacement, sidecar aliases, and backup publication races fail closed.
- New and markerless stores persist the `ROOK` identity before WAL activation.
- Migration, schema repair, and application-ID changes remain inside an immediate transaction and roll back together.
- Backup captures committed live WAL state and verifies the copied database before publication.
- Owner-only Windows DACLs and POSIX modes are enforced for state, sidecars, temporary snapshots, and backups.
- Restore, compaction, retained content, auto-refresh, Linux SSH, and broad operator controls are labeled deferred.
- Current projections and indexed bounded pages keep ordinary UI reads independent from retained-history length.

## Dismissed candidates

- **“Rookery currently has a disk-growth incident.”** Rejected. The actual database is tiny and has no freelist pages.
- **“Restore is falsely advertised.”** Rejected. README explicitly says restore is absent and unverified.
- **“Backup can copy a foreign database.”** Rejected. Immutable identity preflight and regression tests now fail closed.
- **“Backup publication can overwrite or delete a racing competitor.”** Rejected. Guarded identity checks and conditional cleanup are directly tested.
- **“Deferred retention records are fictional current components.”** Rejected. The implementation-status and roadmap sections identify them as deferred.

## Decision impact and repair order

1. Make `run-once` bounded behavior explicit and non-misleading before recommending it for unattended backlog recovery.
2. Add platform durability barriers before treating successful backup completion as power-loss recovery evidence.
3. Require a verified pre-migration backup and explicit no-downgrade warning in upgrade guidance.
4. Add the low-severity storage-growth warning while keeping compaction itself deferred.

After repair, rerun:

- focused 10,001-cycle and idle `run-once` tests;
- backup ordering and flush-failure injection tests on Windows and POSIX;
- upgrade-order documentation checks and a pre-migration backup regression;
- exact Windows and Ubuntu/WSL full gates;
- installed-wheel backup/CLI smoke and the real ignored-database integrity/ACL checks.
