# Rookery critical review: operator authority and durable retirement

Reviewed: 2026-08-30 04:42 ET  
Mode: fresh first-look, technical/product deep dive, patch-after-review  
Decision influenced: whether an operator can uniquely attribute cached facts and safely pause, restore, or retire one remote authority after verified-authority migration

## Scope and evidence

This review used current committed source, the rendered post-0019 dashboard, read-only immutable queries against the real local database, existing reconciliation/action tests, and two independent review passes. The real state contains one enabled verified `TAP` authority, one paused legacy `TAP`, and one paused legacy `primary-workspace`; each owns root objects with duplicate visible names.

The rendered dashboard passed Lighthouse 100 in all audited categories and had no console errors. The findings concern semantic attribution and lifecycle control, not visual polish or accessibility.

## Overall assessment

One high and five medium findings survive. The high is direct operator-truth failure: authority identity exists in durable state but disappears from the visible fact/action/alert/refresh surfaces. The medium findings cover false historical-cache diagnosis, a setup placeholder that creates a doomed durable authority, ownership bypass by `init`/`run-once`, stale work revival after remove/change-back, and the absence of durable retirement.

## What holds up

- The verified authority fingerprint/root actually separates canonical caches.
- Exactly one real authority is enabled; refresh construction and final guards exclude disabled authorities.
- The per-database OS lock is crash-safe because lock ownership, not file existence, controls admission.
- Pre-fingerprint caches remain present and read-only rather than being deleted.
- Cursor and rendered accessibility contracts remain green.

## Findings

### 1. High — active and historical authorities are not uniquely attributable in the UI

Confidence: high  
Evidence quality: A

Observed evidence:

- Two real system cards are named `TAP`; one is enabled/verified and one paused/legacy. Both show the same kind and scopes.
- Inventory rows show duplicate `/` and `Unity Catalog catalogs` objects without system attribution.
- Object detail displays only `System: TAP`, not UUID, config mapping, status, root, or fingerprint state.
- Action and alert views retain/display only `system_name`; action filters can contain duplicate labels.
- Refresh controls hide the decisive system UUID and show no authority marker.

Decision impact: an operator cannot determine which authority produced a fact/action/alert or independently confirm which authority a refresh will query. The verified-authority control is therefore invisible at its main decision surface.

Repair shape: expose full/copyable local system ID, enabled/historical state, workspace root, config ID when known, and a safe fingerprint prefix or explicit `legacy/unverified`. Attribute every object, action, alert, filter option, and refresh control. Add an inventory system filter if cross-authority rows remain in one view.

Verification needed: render the current three-authority fixture and require every duplicate name and every operational/refresh record to be uniquely attributable.

### 2. Medium — paused historical cache is falsely diagnosed as unsupported

Confidence: high  
Evidence quality: A

When only paused systems/capabilities remain, the dashboard says “Refresh unsupported — No observation capability is registered,” although capabilities are registered and authority is merely historical/disabled. Object detail similarly says only “No object refresh available.”

Decision impact: the operator is directed toward an adapter/capability problem rather than the real remedy: configure or restore an authority.

Repair shape: distinguish no systems, historical/paused authority only, capability unsupported, and worker unavailable with actionable text.

### 3. Medium — the generated zero fingerprint can create a guaranteed first-refresh failure

Confidence: high  
Evidence quality: A

`init-config` writes an all-zero fingerprint and standalone setup does not make replacement an explicit pre-init step. The sentinel passes configuration/init, creating a durable placeholder authority. `doctor` does not check the profile authority; first refresh fails, and later correction creates a second authority while pausing the placeholder.

Repair shape: reject the zero sentinel for stateful runtime construction before database creation/reconciliation, with an exact `fingerprint-profile` remediation. Installed-wheel smoke must prove untouched template fails early and edited fingerprint initializes once.

### 4. Medium — `init` and `run-once` bypass live database ownership

Confidence: high  
Evidence quality: A

Only `serve` holds the database lock. `init` and `run-once` invoke the same configuration reconciliation/runtime path without it, so a second process can rotate/disable the running serve authority; `run-once` can also start a competing worker.

Repair shape: hold the same database lock for the complete `init` and `run-once` lifetimes. Keep online backup read-only and exempt.

### 5. Medium — pre-removal work can revive after exact authority change-back

Confidence: medium-high  
Evidence quality: A

Removal disables current resources but does not terminalize pending/deferred scopes or queued/retry actions. Exact fingerprint/root change-back restores the same durable IDs, so an old action can pass the current enabled-state guard and dispatch after reactivation.

Decision impact: stale work can consume remote quota/audit effects even though it predates the operator's removal boundary.

Repair shape: when an authority leaves desired state, transactionally terminalize its non-running intent scopes and queued/retry/pre-running actions, preserving audit links and allowing already-running work only under existing safe semantics. Verify remove → restore before worker yields zero runner calls for old work.

### 6. Medium — historical authorities cannot be permanently retired while preserving cache

Confidence: high  
Evidence quality: A

Historical mappings are automatically reusable whenever the same config ID/fingerprint/root returns. There is no retired tombstone, authority inventory command, or explicit unretire path. Operators cannot preserve cache while ensuring an authority cannot reactivate accidentally.

Repair shape: add durable retired state keyed by system/config authority, bounded authority inventory, and explicit retire/unretire commands. Reconciliation must refuse automatic re-enable while retired; cached facts remain readable.

## Decision order

1. Make authority attribution visible and reject placeholder authority before state creation.
2. Extend database ownership to all stateful runtime commands.
3. Terminalize stale pre-removal work.
4. Add durable retire/unretire plus inventory and surface it in the UI.

Every slice requires independent review, exact Windows/Ubuntu gates, real-database backup/migration if schema changes, and a committed Murmuration follow-up.
