# Rookery critical review: recovery, release evidence, and operator truth

Reviewed: 2026-08-30 02:06 ET  
Mode: fresh first-look, technical deep dive, patch-after-review  
Decision influenced: whether the current local project is clean enough to treat its queue recovery, cached inventory, packaged distributions, and CI evidence as trustworthy

## Scope and materials reviewed

This review was rebuilt from the current repository and runtime surface rather than from the two prior review reports. It covered:

- all 28 Python source modules, 18 SQLite migrations, 8 templates, 4 static assets, and 13 test modules;
- the six-command CLI and eleven registered HTTP routes;
- queue leasing, retry recovery, SQLite contention, backup publication, and runtime supervision;
- `README.md`, `docs/architecture.md`, `pyproject.toml`, `uv.lock`, build constraints, CI, Dependabot, and `scripts/verify_distribution.py`;
- the current wheel and sdist, an independent constrained wheel rebuild from the sdist, and a fresh Windows test run;
- three independent read-only review passes for recovery behavior, public/documentation truth, and release-evidence integrity.

The fresh Windows run passed 493 tests with 8 documented platform skips. The inspected wheel and sdist currently match the source bytes that were compared, and rebuilding the wheel from the sdist under the hash-constrained build graph produced the same SHA-256 as the directly built wheel. Those facts are important: several findings concern what the automated gate can prove, not a demonstrated defect in the current archive bytes.

## Overall assessment

Rookery's core safety posture holds up unusually well: state is loopback-only, browser access is capability-gated, remote work is closed to registered observation commands, queue mutations are transactional, malformed queued contracts are already quarantined, and backups have explicit file/directory durability barriers.

Eight medium findings survive. The most consequential are a durable-work wedge caused by malformed state-dependent timestamps, an unconstrained build backend executing before the constrained release build in CI, and a distribution verifier that does not bind all executable/metadata bytes to the reviewed source. The remaining findings are material truth or availability gaps rather than evidence of remote-state corruption.

## What holds up

- Existing normal queue writes preserve lease, retry, and action invariants transactionally; the poison cases require corruption, legacy/manual mutation, or a defective older writer.
- Current Windows tests pass 493/8, and the previously recorded Ubuntu/WSL gate passes 495/6.
- The current sdist independently rebuilds a byte-identical wheel with the committed hash-constrained build graph.
- The current wheel's package tree matches the current source tree in a direct ad hoc comparison, and its metadata declares the three intended runtime dependencies.
- Complete-membership reconciliation is conservative: unknown collection coverage never infers absence, and complete evidence is rejected if it would be split unsafely across ingestion batches.
- Recovery documentation now explicitly distinguishes a durable backup from an implemented restore workflow and warns that history and backups are uncompacted.

## Findings

### 1. Medium — malformed lease/retry timestamps can permanently wedge durable work

Confidence: high  
Evidence quality: A

Observed evidence:

- `SQLiteStore._promote_due_intent_scopes` promotes leased scopes only when `leased_until <= now`.
- `SQLiteStore._promote_due_actions` promotes leased/running actions only when `leased_until <= now` and retries only when `retry_at <= now`.
- `NULL` and values such as `not-a-timestamp` fail those comparisons. The claim path only selects `queued` scopes or `ready` actions afterward.
- Active actions retain the unique dedupe key while in `leased`, `running`, or `retry_wait`, so equivalent requests continue coalescing onto the poisoned action.

Decision impact: one damaged row can leave an intent open and block refreshes for one exact dedupe scope indefinitely. Normal current writes should not create it, but recovery code must contain corrupt or legacy state rather than relying on ideal writers.

Repair shape: before ordinary due promotion, run a bounded poison sweep for state-dependent lease/retry fields. Reuse the existing idempotent intent/action contract terminalizers so linked aggregates close, dedupe authority is released, and one redacted alert is emitted.

Verification needed: inject `NULL` and malformed timestamps into leased intent scopes and leased/running/retry-wait actions; prove healthy work progresses, linked receipts terminalize, and repeated claims do not duplicate alerts.

### 2. Medium — CI executes an unconstrained build backend before the constrained release build

Confidence: high  
Evidence quality: A

Observed evidence:

- The project declares Hatchling in `[build-system]`.
- CI begins with `uv sync --locked --group dev`, which installs/builds the local project.
- Hatchling and its build-time graph are not part of the runtime/dev lock graph; the committed hash constraints are supplied only to the later `uv build` command.

Decision impact: a drifting or compromised build dependency can execute before lint, tests, and packaging, outside the boundary described as hash-pinned release evidence.

Repair shape: sync the locked development graph with `--no-install-project`, run tools with `uv run --no-sync`, and allow backend execution only in the hash-constrained build and sdist-rebuild steps.

Verification needed: a cold, isolated CI-equivalent environment must sync and run the test gate without installing the project, then build successfully only through the constrained command.

### 3. Medium — distribution verification does not bind all executable and metadata bytes

Confidence: high  
Evidence quality: A

Post-review adjudication correction: the pinned `uv build` command currently reports that it builds the wheel from the newly created sdist, so sdist buildability was already exercised by the build tool. The surviving finding is the missing exact source/module/metadata/RECORD assertions. An explicit second sdist rebuild remains useful as independent, byte-identity evidence, but it is hardening rather than remediation of an absent first build.

Observed evidence:

- `verify_wheel_runtime_assets` compares only migrations, templates, and static files with current source.
- Python modules, `METADATA`, and `RECORD` are outside that check.
- The installed smoke preinstalls dependencies, installs the wheel with `--no-deps`, and exercises imports/help/initialization; it does not prove that dependency metadata or all unexercised module behavior matches the reviewed source.
- The verifier does not rebuild a wheel from the sdist, even though the current sdist does rebuild to a byte-identical wheel when checked manually.

Decision impact: a stale or altered Python module, missing dependency declaration, unexpected package file, damaged RECORD, or source archive that cannot reproduce the reviewed wheel could pass more of the release gate than the status language implies.

Repair shape: enforce an exact package-file manifest and byte parity for every module/runtime asset; validate normalized project metadata and wheel dependency metadata; verify RECORD digests; rebuild the wheel from the sdist under the same hash constraints and require byte identity with the directly built wheel.

Verification needed: negative tests must mutate a module, add an unexpected package file, remove a dependency declaration, corrupt RECORD, and make the sdist-derived wheel differ.

### 4. Medium — the reported branch-coverage floor is a combined coverage floor

Confidence: high  
Evidence quality: A

Observed evidence:

- `branch = true` records branch outcomes, but coverage.py's ordinary `coverage report` total and `fail_under` combine statements and branches.
- The recorded Ubuntu/WSL data used by the review contains 5,333/5,941 covered statements (89.77%) and 1,437/1,870 covered branches (76.84%), while the displayed combined total rounds to 87%.
- `current-status.md` repeatedly calls the displayed combined percentage “branch coverage.”

Decision impact: the gate is green, but it does not enforce the metric the status says it enforces. This weakens the credibility of otherwise strong quantitative evidence.

Repair shape: publish statement-only, branch-only, and combined percentages separately. Keep the existing 80% combined floor and add an explicit honest branch-only floor that current supported platforms meet, or add tests until a chosen higher floor is real.

Verification needed: a deterministic coverage check must fail when branch-only coverage falls below its declared floor, independently of the combined result.

### 5. Medium — unknown collection completeness is presented too much like current inventory

Confidence: high  
Evidence quality: A

Observed evidence:

- Every Databricks Workspace and Unity Catalog list normalizer currently declares `CollectionCoverage.UNKNOWN`.
- Unknown coverage correctly prevents omitted children from being marked absent; a later A-only result cannot remove B from an earlier A+B result.
- The membership facet can nevertheless render `current`, the README advertises “current direct children,” and the children section does not expose collection completeness.
- The architecture's complete-membership behavior exists, but the current chunker deliberately rejects complete evidence spanning multiple ingestion batches.

Decision impact: operators can read a recent successful list as proof that the displayed set is current, even though each relationship is only last-positive evidence and removals remain unconfirmed.

Repair shape: retain conservative unknown coverage, label the section “last-observed children,” include `collection_completeness: unknown` in membership evidence, and remove the current-set claim. Do not switch to complete absence reconciliation until exhaustive-result and multipart atomicity contracts are implemented together.

Verification needed: A+B followed by A must still preserve B, while the object view and packaged README explicitly explain that omission is not absence.

### 6. Medium — SQLite contention and local queue batches can freeze the HTTP event loop

Confidence: high  
Evidence quality: B

Observed evidence:

- The shared store uses synchronous SQLite operations on the FastAPI event-loop thread with a 5,000 ms busy timeout.
- Runtime supervision executes up to 100 coordinator iterations and 100 worker iterations; locally resolved work may complete without a yielding await, and a `worked` loop immediately starts another pass.
- Multi-process queue coordination is intentionally supported through `BEGIN IMMEDIATE`, so lock contention is not merely a forbidden deployment mode.

Decision impact: one competing writer can pause every route for seconds, and a large locally resolved queue can starve cached reads, contradicting the product's availability posture during worker degradation.

Repair shape: sharply bound the event-loop SQLite busy timeout and yield after each bounded background batch. A future dedicated persistence executor may be warranted, but is not required for the smallest safe repair.

Verification needed: under a held external write lock, a background claim must fail/retry within the bounded timeout and an event-loop heartbeat must continue; a long locally resolved batch must yield between bounded chunks.

### 7. Medium — standalone wheel users cannot reach the contract-bearing architecture document

Confidence: high  
Evidence quality: A

Observed evidence:

- The wheel-only installation path says no source checkout is required.
- The README embedded in wheel metadata links to relative `docs/architecture.md`.
- The wheel contains neither that file nor a stable project/documentation URL; only the sdist contains it.

Decision impact: checkout-free operators cannot discover the document that defines deferred/current boundaries, collection semantics, recovery limits, and the security model from the distributed artifact itself.

Repair shape: package the architecture document from its single source of truth and add a no-overwrite CLI export command, unless and until a stable public documentation URL exists.

Verification needed: a wheel-only install from an empty directory must export a byte-identical architecture document without accessing the checkout.

### 8. Medium — CI discards the exact archives it verifies

Confidence: high  
Evidence quality: A

Observed evidence:

- Both CI matrix jobs stop after building and verifying `dist`.
- There is no artifact upload, digest handoff, attestation, or release step.

Decision impact: a later separately rebuilt or replaced archive can be distributed while citing the same green CI run. The run currently proves ephemeral bytes, not the bytes available for handoff.

Repair shape: upload each matrix job's already-verified `dist/*` under an OS-specific artifact name with failure-on-missing behavior and bounded retention. A future release workflow should consume those bytes without rebuilding.

Verification needed: workflow artifacts must expose digests and preserve the exact wheel/sdist pair produced by the verified commit.

## Material omissions and rejected alternatives

- The review did not treat missing live Databricks validation as a defect because the project consistently labels it unverified and refuses to guess a profile.
- It did not recommend changing list results directly to complete coverage. Official CLI source evidence says the supported list commands exhaust iterator pages, but current ingestion deliberately cannot apply one authoritative complete boundary across split batches. Truthful labeling is safer than partial absence authority.
- It did not require a restore command in this round because backup-without-restore is now explicit in both operator and architecture documentation.
- It did not promote the 5,847-line SQLite module or the 26 functions above Ruff's default complexity threshold to findings by themselves. Those are maintenance signals, not demonstrated defects; the concrete recovery and event-loop findings are the actionable consequences.
- Artifact attestation would strengthen provenance, but retaining exact verified bytes is the bounded first repair; publishing and external release authority remain outside this local task.

## Open questions

No user decision is required for the repair round. The following are future design decisions, not blockers:

- whether authoritative complete collections should be staged across bounded batches before one atomic coverage commit;
- whether the long-term SQLite boundary should move to a dedicated executor/thread rather than using a bounded event-loop timeout;
- what stable repository/documentation URL should replace installed documentation export once this project has an external home.

## Decision impact

The project is fit for continued local improvement, but the current evidence should not yet be described as fully release-bound or fully recovery-complete. The repair order is:

1. contain malformed durable timestamps and event-loop starvation;
2. remove unconstrained pre-gate build execution;
3. make package/source/sdist/metadata verification exact;
4. make coverage, collection, and installed-documentation claims truthful;
5. retain the exact CI-verified archives.

After those changes, rerun the exact Windows and Ubuntu/WSL gates, rebuild twice, rebuild from the sdist, compare hashes, and obtain an independent post-fix review.
