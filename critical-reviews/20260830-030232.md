# Rookery critical review: authority identity, bounded work, and executable schema

Reviewed: 2026-08-30 03:02 ET  
Mode: fresh first-look, technical deep dive, patch-after-review  
Decision influenced: whether Rookery can safely preserve one canonical remote identity and remain predictably responsive as local queues and retained history grow

## Scope and materials reviewed

This review starts from current source after the closed 02:06 release/recovery round. It covers:

- Databricks configuration identity, profile changes, binding reload, and cached-object continuity;
- `serve` ownership, loopback reservation, configuration reconciliation, and failed-launch side effects;
- due queue promotion, claim loops, background batching, and VM-step bounds;
- dashboard, object, action, and alert pagination/count query structure;
- immutable SQLite preflight, migration-derived DDL, runtime index repair, triggers, and operational-event integrity;
- three independent read-only first-look passes for boundedness, operator lifecycle, and residual local security.

No prior report was used as an outline. The prior reports were checked only after findings were formed; none of the findings below is already recorded as open.

## Overall assessment

One high and four medium findings survive. The high finding is an authority-boundary defect: changing a stable configuration to a different profile deliberately reuses one system identity even though profile names can select different workspaces. The four media concern failed-launch mutation, queue work amplification, unbounded page work, and executable schema objects that are outside the migration-derived allowlist.

The prior package/recovery fixes remain intact. No new credential disclosure, browser-authentication bypass, remote mutation path, or archive defect was established.

## What holds up

- Same-profile credential rotation remains possible without storing secrets; the problem is changing the profile reference while retaining authority identity.
- Socket reservation is dual-stack and exclusive; the side effect occurs because reservation happens after configuration commit, not because reservation itself is weak.
- Each promotion transaction is capped at 1,000 rows and yields between transactions; the defect is the outer loop draining every batch before one claim.
- Response payloads and page sizes are bounded, and ordinary first-page plans use intended indexes; the defect is exact totals and deep OFFSET work, not unbounded response memory.
- Expected schema DDL is already derived from migrations and required runtime indexes can be repaired safely; exact allowlisting can reuse those mechanisms.

## Findings

### 1. High — changing the profile reference can merge different workspaces into one canonical system

Confidence: high  
Evidence quality: A

Observed evidence:

- Explicit identity lookup uses `config_id` plus `workspace_root`; profile is absent from `authority_key` and the derived stable UUID.
- Reconfiguration then updates the retained binding's `profile` field.
- Every later dispatch resolves the current binding and passes that profile to the Databricks CLI.
- Existing tests intentionally assert `PROFILE_ONE → PROFILE_TWO` preserves the same system ID.
- Unknown collection completeness means objects seen only in the former workspace are not removed by the first list from the latter workspace.

Reproducible trigger: refresh profile A under `id = "primary"`, root `/`; stop; change only the profile to B where B names another workspace; restart and refresh. A-only objects remain under the same system while B observations enter that identity, and colliding source keys can overwrite projection values.

Decision impact: the dashboard can present a blended inventory from two remote authority domains as one canonical system. This breaks the core identity/provenance contract and can mislead operational decisions.

Repair shape: make the profile reference part of the conservative authority key and stable system derivation. A profile-name change creates a new system/cache authority and disables the predecessor. Credential rotation remains supported inside the same named profile. A future explicit immutable workspace-host/ID witness may permit safe profile-name changes, but should not be guessed now.

Verification needed: same ID/root/profile plus display-name changes preserve one system; a changed profile produces a distinct enabled system and disabled predecessor; changing back re-enables the original authority/cache without merging.

### 2. Medium — a failed `serve` launch can mutate a running instance's durable configuration

Confidence: high  
Evidence quality: A

Observed evidence:

- `main()` constructs the stateful runtime before `_serve_loopback()` reserves listeners.
- Runtime construction atomically reconciles the desired configuration, including profile changes and disabling removed systems.
- A second process can therefore commit changed configuration and only afterward fail because the first process owns the port.
- The first process reads current bindings at dispatch, so it observes the second process's durable mutation while continuing to run.

Decision impact: the operator sees an exit-2 failed launch but the supposedly unchanged running service can already have different future dispatch authority.

Repair shape: reserve both listeners before stateful runtime construction and hold a database-scoped exclusive serve lock so an alternate-port second instance also fails before reconciliation. Release sockets/lock on every failure.

Verification needed: with instance A holding the database/port under profile P1, instance B using P2 must exit without changing database bytes or A's binding. After A releases ownership, B may apply P2 once.

### 3. Medium — one nominal queue claim drains the whole due backlog before leasing one item

Confidence: high  
Evidence quality: A

Observed evidence:

- Promotion transactions are capped at 1,000 rows.
- Both intent and action claim paths call promotion in a `while` loop until fewer than 1,000 remain.
- The existing 5,000-row intent regression expects one claim to leave one leased row and all 5,000 other due rows already queued.

Decision impact: after an outage or synchronized retry boundary, one coordinator/worker iteration performs O(due backlog) writes before returning one item. Transaction size is bounded, but request/event-loop work is not.

Repair shape: promote at most one fixed batch per claim invocation, then lease from available work. Leave the remainder deferred/retrying for subsequent bounded ticks.

Verification needed: intent and action regressions must show one call changes no more than one promotion batch plus one lease, with VM steps insensitive to a much larger due backlog; repeated calls must make progress without loss.

### 4. Medium — bounded page payloads still perform unbounded exact counts and deep OFFSET scans

Confidence: high  
Evidence quality: A for query structure; runtime magnitude not yet measured

Observed evidence:

- Object, relationship, action, and alert page composition executes an exact `COUNT(*)` before a `LIMIT … OFFSET` query.
- Object substring search uses a leading wildcard.
- Accepted page numbers allow offsets up to tens of millions of objects and roughly one million retained actions/alerts.
- These synchronous queries execute on the same event loop and connection used by cached pages.

Decision impact: retained history or inventory growth can make a request expensive even though at most 50/100 rows are returned. Deep pages can block other loopback requests.

Repair shape: replace page-number/OFFSET navigation with stable keyset cursors and `limit + 1` lookahead; avoid exact totals on every request or maintain bounded summaries. Treat substring search separately because it cannot be made index-bounded by pagination alone.

Verification needed: query-plan and progress-handler tests over 10× row growth must keep next-page VM steps approximately constant for unfiltered navigation, while search is explicitly labeled and bounded by a separate policy.

### 5. Medium — immutable schema validation accepts unrecognized executable triggers

Confidence: high  
Evidence quality: A

Observed evidence:

- Immutable preflight proves an initial-schema subset, not the exact DDL set for the recorded migration version.
- Current-schema validation checks each expected DDL object but does not reject extra objects.
- An extra trigger on `operational_events` can delete each inserted runtime event after startup accepts the database.

Reproducible trigger: create a valid closed store, add an `AFTER INSERT ON operational_events` trigger that deletes `NEW.idempotency_key`, then reopen. Startup currently accepts it; `record_runtime_failure()` loses its row and faults.

Decision impact: an unexpected trigger is active SQL code that can falsify state or diagnostics despite later filesystem hardening. The owner-only local boundary limits reachability, so this remains medium.

Repair shape: during immutable preflight, require exact migration-derived user-schema DDL for the last recorded version, allowing only required runtime indexes to be absent/mismatched for the existing repair path. After migration/repair, require exact equality for tables, indexes, triggers, and views.

Verification needed: extra table/index/trigger/view stores must fail before write-capable open without changing bytes, journal mode, or sidecars; missing/mismatched required runtime indexes must still repair atomically.

## Material omissions and decisions

- The profile itself is not proof of remote workspace identity. Making it part of the authority key is the conservative no-question repair, not a claim that two profile names can never target the same workspace.
- Listener-first startup alone does not prevent a second serve on another port; database-scoped ownership is required for the full failed-launch contract.
- Keyset pagination changes public query/navigation shape and therefore should be implemented as one coherent UI/backend slice rather than patched with a lower arbitrary page cap.
- The 50,000-deferred-row startup timing scan measured about 0.51 seconds locally. It is linear and merits watching, but no separate medium finding was promoted because it occurs once at startup and validates durable recovery state.

## Decision impact and order

Do not retain profile-name changes as one authority. Repair in this order:

1. profile authority identity and failed-serve ownership;
2. exact schema allowlisting;
3. one-batch queue promotion;
4. keyset navigation and count removal.

Each slice requires an independent post-fix review and exact Windows/Ubuntu gates before closure.
